Extraction performs padded tokenization before recording the hash (`src/vjp_steering/j_lens_concept.py:353-365, 372-378, 757`), while cache validation recomputes it after a fresh model/tokenizer load (`scripts/experiment.py:261-280, 440-447`). - **Correct:** The Modal extraction-only path invokes the dedicated experiment entrypoint, commits the volume, and returns extraction metadata (`scripts/run_modal.py:66-83, 346-365`). - **Finding: P1 — the new tokenizer hash is stable but does not sufficiently identify tokenization behavior.** `get_vocab()` does not encode BPE merge ranks, normalizer, pre-tokenizer, post-processor, decoder, or AddedToken flags; converting special tokens to `str` also discards AddedToken behavior (`src/vjp_steering/j_lens_concept.py:84-90`). Two tokenizers can therefore have identical values for all three hashed fields while producing different token IDs for the same rendered prompt. The source hash only covers prompt strings (`scripts/experiment.py:263-275`), and the suffix check covers only the final assistant suffix (`scripts/experiment.py:249-258`). Although extraction stores the actual tokenization in `token_records` (`src/vjp_steering/j_lens_concept.py:349-365, 586-593, 768`), cache validation never compares it. This is especially relevant because observed v11 metadata has `tokenizer_revision: null` (`outputs/experiments/j-lens-persona-components-tiny-smoke-v11/extraction/metadata.json:848-850`). Consequently, a tokenizer with changed segmentation but the same vocabulary/template can silently reuse incompatible vectors at `scripts/experiment.py:440-463`. Smallest robust fix: record and validate a hash of the unpadded token-ID sequences for all 600 extraction prompts. Alternatively, canonicalize `backend_tokenizer.to_str()` as JSON while removing only mutable runtime padding/truncation fields. Add tests showing the hash remains unchanged after padded batching but changes when merge/normalizer or AddedToken behavior changes.

- **Finding: P1 — default J-lens provenance is not validated on cache reuse.** Persona extraction depends on `_load_j_lens()` (`src/vjp_steering/j_lens_concept.py:594`), but `implementation_hash()` hashes only `j_lens_concept.py` (`src/vjp_steering/j_lens_concept.py:76-77`), excluding the loader and its default lens constants in `src/vjp_steering/vjp.py:137-139, 416-431`. Cache validation compares `lens_sha256` only when `args.lens_file` is explicitly supplied (`scripts/experiment.py:393-394`). The real-Qwen Modal entrypoint exposes no lens-file argument (`scripts/run_modal.py:346-365`), so it uses the default lens. A changed default lens file, revision, or loader can therefore leave the implementation hash unchanged and silently accept vectors extracted with a different lens. The tiny smoke does not cover this path because it explicitly sets `args.lens_file` before extraction and reload (`scripts/concept_checks.py:602-627`). Smallest fix: resolve the default lens on cache hits and compare its content hash, or pin and validate an immutable lens commit/content identity.

- **Merge verdict: BLOCK.** The v10 padding-state failure is fixed, but v11 can still silently accept artifacts produced by incompatible tokenization or a different default J-lens. Fix these cache-identity gaps before the real-Qwen extraction-only run.
